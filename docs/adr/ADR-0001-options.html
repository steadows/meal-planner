Runtime model: how the bot and the Saturday jobs run

Three ways to run the always-on pieces on this Mac: the Telegram bot, the "on it… here's your answer" background work, the Saturday/Sunday schedule, the one-Chrome-at-a-time cart fill, and what happens after a restart.

Record (2026-09-25): Steve selected Option B. It became docs/adr/ADR-0001-runtime-model.md, which supersedes the details here: the debate added reconcile (five plists), and the job_run migration number is set at merge.

What the research settled

macOS catches up on missed schedulesA launchd calendar job due while the Mac sleeps runs on wake; several missed intervals coalesce into one run. cron skips them. Powered-off time is not covered, so run once at startup too.
launchd.plist(5), StartCalendarInterval
Claude works from a background job hereTested on this Mac: a launchd one-shot ran claude -p --safe-mode with the key stripped, answered "ready", rc 0, 3 s.
local test, Claude Code 2.1.280; cf. #77213 (closed, not reproduced), #95689 (open, avoided by safe mode)
The bot library's scheduler drops missed jobsPTB JobQueue uses APScheduler with a 1-second misfire grace; a job due while down/asleep is skipped, and jobs aren't persisted across restarts.
PTB wiki "Making your bot persistent"; APScheduler 3.x defaults
Other processes can send as the botOnly two concurrent getUpdates pollers conflict (409). A job process can call sendMessage with the same token while the bot polls.
Bot API getUpdates; consistent community reports (inferred, not stated by Telegram)
Graceful stop waits for in-bot tasksPTB awaits create_task work on stop, but launchd SIGKILLs after ExitTimeOut (20 s default), so a 10-minute run inside the bot dies on a restart.
PTB Application docs v22.8; launchd.plist(5)
Chrome runs in your logged-in sessionCart fills need Chrome open with the Meijer profile; a LaunchAgent (your GUI session) can reach it. Two profiles have the extension, so the cart spike must prove which one an unattended run drives.
code.claude.com/docs/en/chrome

Recommendation: B. It lets macOS do what it already does well (on-time and on-wake scheduling, restarts) and keeps the long, side-effecting cart fill out of the bot's process. It costs one tiny command-line entry point and a few plist files, not a queue.

Needed from contracts under A or B: a job_run table (job, week_start, started_at, finished_at, outcome, primary key (job, week_start)) in migration 1, before contracts merges. It's what makes "nudge once", "don't double-fill the cart after a crash" and "retry cart" work. Adding it later means a second migration.
